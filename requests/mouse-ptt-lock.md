Today: fluidvoice/hotkey.py is keyboard-only (XGrabKey). Hold mode already solves the hard part of push-to-talk on X11 for keys: the XGrabKey activation is released for the hold's duration so other keys pass through natively, release is detected by auto-repeat-proof query_keymap() polling, a passive Escape grab covers cancel-during-hold, and the grab re-arms afterwards. Nothing suppresses the hotkey when the session is locked - a locked screen with an active dictation keeps the daemon recording, and hotkey presses under the lock screen still toggle state.

Scope:
1) Mouse PTT config: new keys recording.push_to_talk_button (e.g. "button8" / "b8", empty = off) and an optional modifier qualifier; doctor reports resolution.
2) XGrabButton listener: a MousePTTListener in hotkey.py (same file - shared lock-mask/polling helpers, or a sibling module if the planner prefers - keep the pattern) mirroring the hold-mode design: grab_button with owner_events=False, GrabModeAsync; press starts recording and releases the grab activation (ungrab_keyboard) so clicks pass through; release detected by pointer-button-state polling (Xlib query_pointer button mask, auto-repeat immune by nature); re-grab after release; Escape cancel grab armed during the hold, same as keyboard holds. Buttons 1-3 must be refusable (config validation) - a primary-button PTT breaks the desktop.
3) Lock suppression: daemon watches the logind PrepareForSleep/Lock/Unlock D-Bus signals (org.freedesktop.login1 / .session object for this session; fall back to the screensaver D-Bus name where logind Lock is not emitted) - while locked: ignore hotkey callbacks (log once per transition, do not swallow into recording state), cancel any active recording with the existing cancel path, and the tray tooltip notes "paused (locked)". Config key general.pause_when_locked = true default.
4) Tests: unit - button-name parsing/validation, lock-state machine transitions (locked ignores toggle, active recording cancels, unlock resumes normal); integration - XGrabButton arm/hold/release on a spare button (the TEST_CONFIG pattern from tests/integration/, using an uncommon button or accepting XTEST pointer events; if XTEST pointer fakes are unreliable live - the keywork predecessor found Xorg drops state-matching fakes - then the integration test may drive the listener's internal poll with synthetic state, and the live arm is asserted via the status hotkey_grabbed-style surface).

Where: fluidvoice/hotkey.py (MousePTTListener or sibling), fluidvoice/daemon.py (wiring, lock watch, recording cancel on lock), fluidvoice/config.py (new keys + template comments), fluidvoice/doctor.py, tests/test_mouse_ptt.py (new), tests/test_lock_suppression.py (new), tests/integration/test_live_x11.py (append case if live-driven).

Done means: a phased plan under specs/ where each phase leaves `.venv/bin/python -m pytest -q tests --ignore=tests/integration` green; a configured spare mouse button starts/stops dictation live with clicks during the hold reaching the focused window; locking the session with dictation active cancels it and hotkey presses while locked are ignored (verified via unit state machine + a live manual-check note); default config (no button set) changes nothing.

Out of scope: gesture support, scroll-button PTT, per-app button overrides, Wayland pointer protocols (X11 only - the Wayland request is separate), any UI editor beyond config keys + doctor lines.
